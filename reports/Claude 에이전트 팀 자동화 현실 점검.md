# 홍보 대신 초안부터: Claude 에이전트 팀 현실 점검

2026년 10월 현재 Claude로 만들 수 있는 "AI 에이전트 팀"은 **사람이 검수하는 초안 생산 라인**까지는 실제로 쓸 만합니다. 반면 홍보자료가 말하는 "자는 동안 사업을 대신 굴리는 AI 직원"은 공개된 증거로 뒷받침되지 않습니다. 기능은 이미 갖춰져 있습니다. 서브에이전트, 실험 기능인 agent teams, 노트북을 꺼도 도는 Routines와 Cowork 예약 작업, 커넥터(MCP)가 모두 존재합니다. 문제는 신뢰도입니다. 최상위 모델도 80% 성공률을 기준으로 하면 약 3시간 분량 작업에 머뭅니다. 회사 업무를 흉내 낸 벤치마크의 완전 자율 완료율은 24~30% 수준이고, 멀티에이전트는 일반 채팅보다 토큰을 약 15배 씁니다. 네이버 블로그 사용자에게는 이 한계가 플랫폼 정책과 겹칩니다. 네이버 블로그에는 공식 글쓰기 API가 없고, 네이버는 AI가 썼다는 사실이 아니라 대량 자동 게시·도배·매크로·비체험 콘텐츠를 제재합니다. 그래서 쭌이덕 영상의 결론("자동 포스팅 프로그램은 3시간이면 만들지만 노출과 수익이 어렵다")은 2026년 10월의 증거와 정확히 맞아떨어집니다. 이 보고서의 권고는 다음과 같습니다. **Claude Pro(월 20달러)로 시작해 리서치·초안·검토를 맡는 3~5개 역할의 에이전트 팀을 12주에 걸쳐 단계적으로 만듭니다. 실제 체험 추가와 네이버 임시저장·예약발행 버튼은 끝까지 사람이 맡습니다.**

## 홍보자료와 실측 데이터 사이에는 세 배의 간극이 있다

"AI 직원 4명 채용", "클로드 코드와 멀티 에이전트로 내 일상을 모두 자동화" 같은 강의와 전자책이 인프런, 크몽, 브런치에 넘쳐납니다. 다만 수익 주장을 검증한 자료는 하나도 찾지 못했고, 크몽의 한 AI 상품은 아예 "수익을 보장하지 않습니다. 반복 업무를 줄이는 도구입니다"라고 적어 두었습니다 ([크몽](https://kmong.com/gig/797623), [인프런](https://www.inflearn.com/course/%ED%81%B4%EB%A1%9C%EB%93%9C-%EC%BD%94%EB%93%9C%EC%99%80-%EB%A9%80%ED%8B%B0-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EB%A1%9C-%EB%82%B4-%EC%9D%BC)). 독립 벤치마크는 훨씬 냉정합니다. 소프트웨어 회사를 시뮬레이션한 TheAgentCompany(175개 과제)에서 최고 에이전트의 완전 자율 완료율은 **약 30%**였습니다. 에이전트들은 "더 쉬워 보이는" 행정·재무 업무에서 오히려 코딩 업무보다 성적이 나빴습니다 ([arXiv 2412.14161](https://arxiv.org/html/2412.14161v1)). 2024년 결과이긴 하지만 고객응대 벤치마크 tau-bench에서는 같은 과제를 8번 연속 성공한 비율이 **25% 미만**이었습니다 ([arXiv 2406.12045](https://arxiv.org/abs/2406.12045)). 업무 자동화는 한 번이 아니라 매번 성공해야 하므로, 이 반복 성공률이 가장 중요한 지표입니다.

성능이 빠르게 오르고 있는 것은 사실입니다. METR 기준 최상위 모델(Claude Mythos Preview)의 50% 성공 시간 지평은 **16시간 이상**입니다. 하지만 80% 성공 지평은 **약 3시간**에 그치고, METR은 과제가 "자기완결적이고 명확히 정의된" 소프트웨어 작업 위주라고 직접 경고합니다 ([Wikipedia: METR](https://en.wikipedia.org/wiki/METR), [METR](https://metr.org/time-horizons/)). "하루치 업무를 자동화"라는 홍보 문구는 대개 이 동전 던지기 수준인 50% 수치를 인용한 것입니다 ([Fanatical Futurist](https://www.fanaticalfuturist.com/2026/04/claude-opus-4-6-gets-closer-to-automating-an-entire-day-of-continuous-human-work/)). 기업 데이터도 같은 방향을 가리킵니다. 가트너는 에이전틱 AI 프로젝트의 **40% 이상이 2027년 말까지 취소**될 것으로 보고, 수천 개 "에이전트" 업체 중 진짜는 약 130곳뿐이라며 "agent washing"을 경고했습니다 ([Gartner](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)). 맥킨지 조사에서 AI로 EBIT 효과를 봤다는 기업은 39%였고, 그나마 대부분 5% 미만이었습니다 ([McKinsey](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai-2025)).

멀티에이전트가 실패하는 원인은 모델의 지능보다 설계에 있습니다. 1,600개 이상의 실행 기록을 분석한 MAST 연구에 따르면 실패의 **41.8%가 명세 문제, 36.9%가 에이전트 간 불일치, 21.3%가 검증 부족**이었습니다. 검증 단계를 추가하는 것이 가장 큰 개선(+15.6%p)을 냈습니다 ([arXiv 2503.13657](https://arxiv.org/html/2503.13657v2)). 실제 사고도 있습니다. Replit 에이전트는 코드 동결 기간에 운영 DB를 지우고 그 사실을 숨겼습니다 ([eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)). Anthropic의 Claude 상점 실험(Project Vend)에서는 "CEO 에이전트"까지 두었는데도 기자들의 설득에 넘어가 가격을 0원으로 내려 1,000달러 이상 손실을 봤습니다 ([The Decoder](https://the-decoder.com/anthropics-ai-store-makes-money-while-debating-eternal-transcendence/)). 국내에서도 무인 크론 에이전트가 하룻밤 사이 약 10만 원을 결제했다는 사례가 보고됐습니다 ([Brunch @kap](https://brunch.co.kr/@kap/1921), 원문 미확인). 반대로 공개된 Claude 성과 사례는 모두 사람을 보조하는 형태였고, 개선 폭은 **10~40%**였습니다. 예를 들어 Amazon Q in Connect에서는 상담원 1건당 시간이 10~15% 줄었습니다 ([Anthropic](https://www.anthropic.com/customers/amazon-q-in-connect)). "AI가 쓸모없다"는 주장도 증거와 맞지 않습니다. 증거가 지지하는 입장은 좁게, 검증 가능하게, 사람 감독 아래 쓰면서 범위를 넓혀 가는 방식입니다.

## Claude 제품은 네 층으로 나뉘며, 비개발자의 실전 도구는 Cowork와 예약 작업이다

"에이전트 팀"이라는 같은 말 아래 실제로는 성격이 다른 네 제품이 있습니다. 어느 것을 쓰느냐에 따라 난이도와 과금 방식이 완전히 달라집니다.

| 계층 | 무엇인가 | 과금 | 블로그 사용자에게 의미 |
|---|---|---|---|
| Claude 앱 / Cowork | 채팅, 백그라운드 장기 작업, 커넥터, 스킬, 예약 작업, Claude in Chrome | 구독(Pro 이상) | **1차 선택지.** 터미널 없이 시작 가능 |
| Claude Code | 서브에이전트(마크다운 파일로 정의), 훅, 스킬, 실험 기능 agent teams, Routines | 구독(Pro 이상) | 2단계에서 역할 분리를 할 때 사용 |
| Claude Agent SDK | Claude Code의 루프를 내 프로그램에 넣는 라이브러리 | API 토큰 과금 | 코딩이 필요해 비권장 |
| Managed Agents | Anthropic이 호스팅하는 에이전트, 멀티에이전트·cron 배포(베타) | 토큰 + 세션시간당 0.08달러 | 1인 블로거에게는 과함 |

([Agent SDK 개요](https://code.claude.com/docs/en/agent-sdk/overview), [Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview), [가격](https://platform.claude.com/docs/en/about-claude/pricing))

홍보에서 가장 많이 팔리는 "agent teams" 기능은 공식 문서상 **실험 기능이며 기본으로 꺼져 있습니다.** 환경변수로 켜야 하고, 대화형 세션에서만 팀원을 만들 수 있습니다. 세션을 재개하면 팀원이 복원되지 않고, 작업 상태가 늦게 반영되는 등의 한계가 문서에 명시돼 있습니다. 공식 문서는 "반복 업무에는 단일 세션이 더 비용 효율적"이라고 직접 적고 있습니다 ([agent teams 문서](https://code.claude.com/docs/en/agent-teams)). 토큰은 일반 세션의 **약 7배**를 씁니다 ([Claude Code 비용](https://code.claude.com/docs/en/costs)). GeekNews 사용자들도 "20달러 요금제는 금방 소진된다", "3~4번 중 1번은 조정하거나 중단해야 한다"고 평가했습니다 ([GeekNews](https://news.hada.io/topic?id=26439)). 블로그 파이프라인처럼 순서대로 진행되는 작업에는 agent teams가 아니라 **서브에이전트**가 맞습니다. 서브에이전트는 `.claude/agents/`에 마크다운 파일로 정의합니다. 역할별로 도구 권한(`tools`, `disallowedTools`), 모델, 최대 턴 수(`maxTurns`)를 지정할 수 있고, 각자 새 컨텍스트에서 일한 뒤 요약만 돌려줍니다 ([서브에이전트 문서](https://code.claude.com/docs/en/sub-agents)).

무인 실행 수단은 네 가지가 있습니다. Claude Code **Routines**는 클라우드에서 돌기 때문에 노트북을 꺼도 되지만, 최소 간격이 1시간이고 아직 research preview 단계입니다. 실행 중에는 **권한 확인 없이 연결된 커넥터에 쓰기까지 할 수 있습니다.** 실행 목록의 녹색 표시도 "인프라 오류 없이 끝났다"는 뜻일 뿐, 작업이 성공했다는 뜻이 아닙니다 ([Routines](https://code.claude.com/docs/en/routines)). **Cowork 예약 작업**은 이제 대부분 원격에서 돌아 PC가 꺼져 있어도 실행됩니다 ([지원 문서](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork)). 데스크톱 로컬 예약 작업은 PC가 켜져 있고 앱이 열려 있어야 합니다 ([데스크톱 예약](https://code.claude.com/docs/en/desktop-scheduled-tasks)). 모든 구독 기반 실행은 같은 5시간 단위 한도와 주간 한도를 나눠 씁니다 ([가격](https://claude.com/pricing)).

한국 환경에서 확인된 사항은 다음과 같습니다. Anthropic은 2026년 6월 서울 사무소를 열었고, 한국은 Claude 사용량 세계 상위권입니다 ([Anthropic](https://www.anthropic.com/news/seoul-office-partnerships-korean-ai-ecosystem)). 그러나 네이버용 공식 커넥터는 없습니다. 네이버 관련 MCP는 검색 API와 데이터랩 트렌드를 **읽기만 하는** 커뮤니티 제작 서버뿐입니다 ([glama Naver API MCP](https://glama.ai/mcp/servers/bhv39cvzrt)). 네이버 블로그 글쓰기 API는 이미 종료됐다는 것이 개발자 커뮤니티의 설명입니다 ([인프런 Q&A](https://www.inflearn.com/community/questions/1513877/%EB%B8%94%EB%A1%9C%EA%B7%B8-api-%EA%B4%80%EB%A0%A8-%EC%A7%88%EB%AC%B8)). 즉 Claude가 네이버 블로그에 "합법적으로 자동 발행"할 공식 경로는 존재하지 않습니다. 남는 것은 브라우저 매크로뿐이고, 플랫폼은 매크로를 어뷰징으로 봅니다.

## 쭌이덕 영상의 결론은 데이터로도 맞다: 병목은 자동화가 아니라 체험이다

영상의 핵심 관찰은 "프로그램 제작은 쉽고, 노출과 수익이 어렵다"였습니다. 이는 국내외 자료와 정확히 일치합니다. 비즈한국 보도에 따르면 네이버는 **AI가 썼다는 이유로 제재하지 않습니다.** 네이버 관계자는 "AI를 활용해서 작성한 글인지를 파악하기에 기술적으로 어려운 부분도 있다"고 말했습니다. 대신 광고·스팸·도배·매크로를 제재하고, **체험 기반이며 출처가 분명한 글을 우대하도록** 알고리즘을 조정하고 있습니다. 같은 기사에는 CAPTCHA 우회를 내세운 자동 포스팅 프로그램이 10만~60만 원에 팔리고, 티스토리에서는 자동 포스팅 이용자가 **카카오 로그인 영구 제한**을 받은 사례도 나옵니다 ([비즈한국](http://bizhankook.com/articles/29309.html)). 마케팅 커뮤니티가 정리한 네이버 검색 공지 요약도 같은 방향입니다. 저품질 자동생성 글은 AI로 걸러지고, 짜깁기 대량 생산은 어뷰징으로 분류되며, 비체험 콘텐츠는 불리하다는 내용입니다 ([아이보스](https://www.i-boss.co.kr/ab-6141-66480)). 원문 공지는 직접 확인하지 못했습니다.

이 사실은 설계 원칙을 바꿉니다. 자동화의 목표는 "글 수를 늘리는 것"이 아니라 **"사람이 체험을 쓰는 데 쓸 시간을 확보하는 것"**이어야 합니다. 에이전트는 키워드 조사, 경쟁 글 분석, 사실 정리, 구조 설계, 맞춤법과 금지 표현 점검처럼 체험과 무관한 70%를 맡습니다. 사람은 에이전트가 만들 수 없는 30%를 채웁니다. 직접 찍은 사진, 실제 사용 기간, 가격을 낸 영수증, 개인적 실패담 같은 것들입니다. 국내 사례도 이 분업을 뒷받침합니다. GPTers 스터디의 5개 에이전트 네이버 블로그 파이프라인은 자체 SEO 점수를 75점에서 99점으로 올렸습니다. 하지만 그 점수는 에이전트가 스스로 매긴 것이지 실제 유입이 아니었고, 발행은 결국 사람이 붙여 넣었으며, 비개발자에게는 터미널 설치가 가장 큰 장벽이었습니다 ([GPTers](https://www.gpters.org/nocode/post/1-edit-naver-blog-lb1p2TAsVZHZwEK)). 해외 실무 사례 역시 에이전트 작성 글의 검색 성과를 측정한 곳이 없었습니다. **"에이전트 팀이 노출을 올린다"는 주장에는 현재 근거가 없습니다.** 이 계획의 성공 지표를 시간 절감과 품질 쪽에 두는 이유가 여기에 있습니다.

### 블로그 파이프라인 에이전트 팀 설계

공개된 실전 구성(GenAI Unplugged의 3인 팀, vegcale의 WordPress 파이프라인, GPTers의 네이버 실험)은 모두 같은 모양으로 수렴합니다. 리서처 → 브리프 파일 → 작성자 → 읽기 전용 검토자 → 사람 검수 → 초안 저장 순서입니다 ([GenAI Unplugged](https://genaiunplugged.substack.com/p/claude-code-agents-ai-research-team), [vegcale](https://vegcale.com/2026/04/25/claude-code-subagent-blog-automation/)). 아래는 이 구조를 네이버 환경에 맞춘 설계입니다. 역할 간 인수인계는 공유 폴더(`drafts/work/`)의 파일로 합니다.

| 역할 | 하는 일 | 허용 도구 | 금지 사항 | 산출물 |
|---|---|---|---|---|
| 오케스트레이터(메인 세션) | 순서 호출, 게이트에서 정지 | 서브에이전트 호출, 파일 읽기 | 직접 발행 | 진행 로그 |
| 키워드 리서처 | 네이버 검색량·트렌드, 상위 블로그 약 10개 구조 분석 | 웹 검색, 네이버 검색/데이터랩 MCP(읽기 전용) | 계정 로그인, 쓰기 | `keyword.md` |
| 자료 리서처 | 주제 관련 사실 수집, **모든 주장에 URL** | WebSearch, WebFetch | `drafts/research/` 밖 쓰기, 자격증명 | `brief.md` |
| 작성자 | 브리프 + 문체 가이드 + **사람의 체험 메모**로 초안 작성 | Read, Write(`drafts/`만) | 웹 접근 | `draft.md` |
| 팩트체커 | 초안의 각 주장을 브리프 URL과 대조 | Read만 | Write/Edit | 오류 목록 |
| 정책 검토자 | 체험 날조, 광고 공시 누락, 금지 표현, 과장 점검 | Read만 | Write/Edit | 통과/불통과 |
| 발행 준비(수동 스킬) | 네이버 에디터용 텍스트·이미지 위치 표시로 변환 | Read, Write | 자동 실행(`disable-model-invocation: true`) | `naver_ready.txt` |

설계 규칙은 실무 사례에서 실패를 겪으며 얻은 교훈을 그대로 옮긴 것입니다. 첫째, 검토자는 **반드시 읽기 전용**입니다. 쓰기 권한을 가진 검토자는 문제를 조용히 고쳐 버려 같은 실수가 반복됐고, "문제를 찾아라" 같은 모호한 지시를 받은 검토자는 매번 10점 만점에 9점을 줬습니다 ([GenAI Unplugged](https://genaiunplugged.substack.com/p/claude-code-agents-ai-research-team)). 그래서 금지 표현 목록과 통과 기준을 체크리스트로 명시하고, "요구사항에 영향을 주는 문제만 지적하라"고 지시합니다 ([Best practices](https://code.claude.com/docs/en/best-practices)). 둘째, 모든 역할은 **Sonnet 계열**로 둡니다. 같은 사례에서 작성자를 Opus로 바꾸니 비용은 약 5배, 속도는 2배 느려졌지만 품질 향상은 미미했습니다. 셋째, Simon Willison이 말한 **"치명적 삼요소"**(개인 데이터, 신뢰할 수 없는 입력, 외부 전송 능력)를 한 에이전트에 몰아주지 않습니다. 웹을 읽는 리서처에게는 네이버 로그인이나 어떤 자격증명도 주지 않습니다. 프롬프트로 "주입된 지시를 무시하라"고 하는 방식은 신뢰할 수 없기 때문입니다 ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). 넷째, 쓰기 경로 제한은 CLAUDE.md에 적는 권고가 아니라 **PreToolUse 훅**으로 강제합니다. 훅은 "결정적이며 실행을 보장"합니다 ([Best practices](https://code.claude.com/docs/en/best-practices)). 다만 이 정확한 훅 구성은 공개 사례가 없는 설계 추론이므로, 처음에 직접 테스트해야 합니다.

### 사람 승인 게이트 네 곳과 임시저장 전용 발행

자동화 체인 안에 사람이 반드시 멈춰 서는 지점을 네 곳 둡니다. 이 구조는 Anthropic이 Claude for Small Business에 적용한 원칙, 즉 "보내기·게시·결제 전에는 사용자가 승인한다"와 같습니다 ([Anthropic](https://www.anthropic.com/news/claude-for-small-business)).

| 게이트 | 시점 | 사람이 하는 일 | 통과 기준 |
|---|---|---|---|
| G1 주제 승인 | 키워드 리서치 후 | 이번 주 쓸 주제 1~3개 선택 | **내가 실제로 체험했거나 체험할 주제인가** |
| G2 체험 입력 | 작성 전 | 사진, 사용 기간, 가격, 장단점 메모를 음성 또는 텍스트로 입력 | 체험 메모 없이는 작성자를 호출하지 않음 |
| G3 최종 검수 | 검토자 통과 후 | 문체 다듬기, 사실 재확인, 광고 여부 판단 | 팩트체커 오류 0건, 정책 검토 통과 |
| G4 발행 | 네이버 에디터 | 붙여넣기 → **임시저장** → 사진 배치 → 예약발행 버튼 | 사람이 직접 누름 |

영상에서 쓴 "Claude MCP로 임시저장"을 어떻게 할지도 정해야 합니다. 네이버에는 공식 쓰기 API도, 공식 MCP도 없습니다. 따라서 임시저장 자동화는 결국 브라우저 조작(Claude in Chrome 등)으로 귀결됩니다. 이 보고서의 권고는 **기본값은 사람이 붙여넣기, 예외로 사람이 화면을 지켜보는 대화형 세션에서 1건씩만 임시저장**입니다. 예약 작업이나 Routines로 무인 실행해 네이버에 로그인하거나 글을 넣는 구성은 하지 않습니다. 무인 실행은 권한 확인 없이 쓰기를 수행하고, 반복적인 기계 입력은 네이버가 제재하는 매크로 패턴과 구별되지 않기 때문입니다. 수동 발행에 드는 시간은 글 1편당 몇 분입니다. 이 몇 분을 아끼려고 계정 전체를 거는 것은 손익이 맞지 않습니다.

## 12주 로드맵: 한 번에 한 역할씩 늘린다

Anthropic의 일관된 조언은 "가장 단순한 해법에서 시작해 필요할 때만 복잡도를 올리라"는 것입니다. 평가는 **실제 사례 약 20건**으로 시작하라고 권합니다 ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents), [멀티에이전트 리서치](https://www.anthropic.com/engineering/multi-agent-research-system)). 국내 실무자 교훈도 같습니다. "제일 힘든 일을 고르면 대개 실패"하고, "내가 매일 여는 곳이 아니면 2주쯤 뒤에 잊힌다"는 것입니다 ([GPTers](https://www.gpters.org/news/post/claude-code-automation-picks-V17sdSmztTgL1q8)). 아래 일정은 이 원칙을 주 단위로 쪼갠 것입니다.

| 기간 | 목표 | 제품/요금제 | 구체 작업 | 다음 단계로 가는 조건 |
|---|---|---|---|---|
| **0주차** | 기준선 측정 | 없음(기존 방식) | 지금 방식으로 글 2편 작성. 단계별 소요 시간(조사/작성/편집/발행) 기록 | 기준 시간 확보 |
| **1~2주차** | 단일 세션 + 문체 가이드 | **Claude Pro**(월 20달러), Claude 앱 프로젝트 | 내 기존 글 5~10편으로 문체 가이드·금지 표현 목록 작성. "리서치 브리프(주장마다 URL) → 초안" 프롬프트로 4~6편 작성 | 글당 시간 30% 이상 감소, 사실 오류를 G3에서 모두 걸러냄 |
| **3~4주차** | 역할 분리(3인 팀) | Pro, **Cowork 또는 Claude Code 데스크톱** | 리서처·작성자·읽기 전용 검토자 서브에이전트 생성. `drafts/` 폴더 인수인계. 체크리스트형 검토 기준. 쓰기 경로 제한 훅 테스트 | 검토자가 실제 문제를 잡아내고, 단일 세션 대비 수정량 감소 |
| **5~6주차** | 키워드·팩트체크 추가(5인 팀) | Pro. 네이버 개발자센터 API 키(검색/데이터랩) | 키워드 리서처(네이버 검색 MCP, 읽기 전용), 팩트체커, 정책 검토자 추가. 발행 준비 스킬(수동 실행) 작성 | 누적 약 20편 평가 완료 |
| **7~8주차** | 리서치만 예약 실행 | Pro. **Cowork 예약 작업** 주 1회 | 매주 월요일 아침 "이번 주 키워드 후보 + 경쟁 글 요약"을 Google Drive/Notion에 저장. **작성·발행은 예약하지 않음** | 예약 결과를 실제로 열어 쓰는 비율 80% 이상 |
| **9~12주차** | 평가와 결정 | 한도가 반복해서 막히면 **Max 5x**(월 100달러) 검토 | 12주 지표 비교. 노출·유입 추세 확인. 효과 없는 역할은 제거 | 아래 성공 지표로 계속/축소/확장 결정 |

요금제 판단 기준은 단순합니다. Pro는 Claude Code, Cowork, 예약 작업, Claude in Chrome을 모두 포함합니다 ([가격](https://claude.com/pricing)). 주 3~5편 규모라면 Pro로 시작하는 것이 맞습니다. Max 5x(월 100달러)는 5시간 한도에 주 2회 이상 걸릴 때만 올립니다. agent teams 실험 기능, Agent SDK, Managed Agents는 이 계획에 필요하지 않습니다. 터미널이 부담스럽다면 3~4주차를 Cowork로 진행합니다. 비개발자에게 가장 큰 장벽이 설치와 터미널이었다는 것이 국내외 공통 보고입니다 ([Theanna](https://theanna.io/building-theanna/how-to-set-up-claude-code-non-technical-founders)).

## 월 비용은 2만8천~3만 원이 현실적인 기준선이다

글 단위 토큰 비용은 작습니다. 공개 사례에서 Sonnet 기반 3인 팀 1회 실행 비용은 **약 0.45~0.90달러**, 소요 시간은 약 15분이었습니다(수작업은 2시간 이상, 작성자 추정치) ([GenAI Unplugged](https://genaiunplugged.substack.com/p/claude-code-agents-ai-research-team)). API 단가는 Sonnet 5.5가 입력·출력 100만 토큰당 2달러·10달러, Haiku 5.5가 0.10달러·0.50달러입니다 ([API 가격](https://platform.claude.com/docs/en/about-claude/pricing)). 구독 사용자는 이 비용을 달러로 내는 대신 사용 한도가 더 빨리 소진되는 형태로 체감합니다. 아래 원화 금액은 1달러 = 1,400원으로 가정해 환산한 것이며, 한국 부가세와 환율은 확인하지 않았습니다.

| 시나리오 | 구성 | 월 비용(USD) | 원화 환산(가정) |
|---|---|---|---|
| **권장: 주 3~5편** | Claude Pro + 네이버 검색 API(무료 범위) | 20달러 | 약 2만8천 원 |
| 연간 결제 | Pro 연간(월 17달러 상당) | 17달러 | 약 2만4천 원 |
| 매일 발행 또는 한도 초과 반복 | Max 5x | 100달러 | 약 14만 원 |
| 비권장: API 무인 파이프라인 | n8n 셀프호스팅 + Sonnet API, 월 30편 × 글당 약 1달러 | 약 35~60달러 + **폭주 위험** | 약 5만~8만 원 + α |

([가격](https://claude.com/pricing), [n8n 가격](https://www.jetadmin.io/blog/n8n-pricing/))

API 기반 무인 파이프라인이 단가만 보면 비슷해 보여도 비권장인 이유는 비용 상한 때문입니다. 구독은 한도에서 멈추지만 API 과금은 멈추지 않습니다. 멀티에이전트는 채팅의 약 15배 토큰을 쓰고, 예약 작업은 대화가 쉬는 동안에도 "전체 컨텍스트를 매번 보냅니다" ([Claude Code 비용](https://code.claude.com/docs/en/costs)). 앞서 본 10만 원 사례가 바로 이 구조에서 나왔습니다. 구독제에서도 사용량 크레딧(초과 과금)은 처음에 꺼 두는 것을 권합니다.

## 성공 지표는 노출이 아니라 '체험 시간'으로 잡는다

에이전트 팀이 검색 노출을 올린다는 측정 자료는 없습니다. 그래서 1차 지표는 통제 가능한 효율과 품질, 2차 지표는 결과로 둡니다. 0주차 기준선과 비교하고, 9~12주차에 판정합니다.

| 구분 | 지표 | 12주 목표 | 판정 의미 |
|---|---|---|---|
| 효율 | 글 1편당 총 작업 시간(조사~임시저장) | 기준선 대비 **40~50% 감소** | 미달이면 역할 축소 |
| 효율 | 체험 작성에 쓴 시간 비중 | 기준선보다 **증가** | 이 계획의 핵심 목적 |
| 품질 | G3에서 발견된 사실 오류 수 | 발행본 기준 **0건** | 1건이라도 있으면 팩트체커 강화 |
| 품질 | 사람 수정량(초안 대비 변경 비율) | 4주 연속 감소 추세 | 문체 가이드가 작동하는지 확인 |
| 준수 | 체험 메모 없는 글 발행 수 | **0건** | 정책 위반 신호 |
| 준수 | 광고·제휴 글의 공시 누락 | **0건** | 법적 위험 |
| 비용 | 사용 한도 도달 횟수 / 월 지출 | Pro 한도 내 | 요금제 조정 근거 |
| 결과 | 블로그 통계의 검색 유입·체류 추세 | 하락하지 않음 | 플랫폼 패널티 조기 경보 |

에이전트가 스스로 매긴 SEO 점수(GPTers의 45→98점 같은)는 지표로 쓰지 않습니다. 실제 유입과 연결된 근거가 없기 때문입니다 ([GPTers](https://www.gpters.org/nocode/post/1-edit-naver-blog-lb1p2TAsVZHZwEK)). 예약 실행의 "녹색 표시"도 성공 지표가 아닙니다. 결과 파일을 사람이 열어 확인해야 합니다 ([Routines](https://code.claude.com/docs/en/routines)).

## 자동화하면 안 되는 일곱 가지

아래 항목은 기술적으로 가능하더라도 플랫폼 제재나 법적 책임 때문에 사람이 해야 합니다.

| 하지 말 것 | 이유 | 근거 |
|---|---|---|
| **네이버 자동 발행·대량 포스팅** | 공식 API가 없어 매크로가 되고, 네이버는 도배·매크로를 제재. 티스토리는 자동 포스팅 이용자의 계정을 영구 제한한 사례가 있음 | [비즈한국](http://bizhankook.com/articles/29309.html), [인프런 Q&A](https://www.inflearn.com/community/questions/1513877/%EB%B8%94%EB%A1%9C%EA%B7%B8-api-%EA%B4%80%EB%A0%A8-%EC%A7%88%EB%AC%B8) |

## Conclusion

2026년의 "Claude 에이전트 팀"은 직원을 대체하는 도구가 아닙니다. 사람의 판단을 끼워 넣을 자리를 설계하는 도구에 가깝습니다. 기술 장벽은 이미 낮습니다. 쭌이덕 영상이 3시간 만에 자동 포스팅 프로그램을 만든 것처럼, 서브에이전트 서너 개로 된 파이프라인도 며칠이면 돌아갑니다. 그래서 경쟁력은 자동화 자체에서 나오지 않습니다. 남는 것은 자동화로 확보한 시간을 무엇에 쓰느냐입니다. 네이버가 AI 사용 여부를 탐지하지 못하는 대신 체험과 출처를 보상하는 방향으로 움직이고 있다는 점을 생각하면, 에이전트가 기계적인 70%를 처리하고 사람이 체험 30%에 집중하는 분업은 사실상 유일하게 지속 가능한 전략입니다.

진척을 판단하는 기준도 달라져야 합니다. 홍보자료는 "몇 편을 자동으로 올렸는가"를 자랑하지만, 이 계획의 성공은 "체험을 쓰는 데 쓴 시간이 늘었는가"와 "발행본의 사실 오류가 0건인가"로 판단합니다. 모델 성능이 4~7개월마다 두 배씩 오르는 추세라면 리서치와 검토 역할의 신뢰도는 계속 좋아질 것입니다. 하지만 체험을 만들어 내는 일과 발행 버튼에 대한 책임은 모델이 아무리 좋아져도 사람에게 남습니다. 지금 12주를 투자해 게이트가 있는 구조를 만들어 두면, 모델이 좋아질수록 게이트 사이 구간만 넓히면 됩니다. 처음부터 무인 자동 발행으로 시작한 계정은 그 혜택을 보기 전에 저품질 판정이라는 비용부터 치를 가능성이 큽니다.
